文件地图：需求应该送到哪一层？

把仓库当成有标签的工具库：先找货架，再动文件。

先看标签，不要一上来全库搜索

同一句“帮我改一下”，可能指向完全不同的货架。判断标准不是文件名像不像，而是变化由谁负责。

🧰

根目录

项目总说明、轻量公共依赖、连接配置样例与锁文件。

🧭

公共 SDK

SDK 像前台工具箱；包里放共享规则，保持轻量。

📨

服务 API

API 目录里的 client 负责发送，contract 负责规定请求与响应形状。

🏭

独立 runtime

runtime 放模型实现、服务进程、CUDA 与重型依赖。

🔌

配置

配置告诉 client 去哪里找服务；本机地址变化通常先看 endpoints 文件。

🧪

示例・测试・文档

examples 教怎么用，tests 防止旧功能被改坏，docs 解释怎么安装、排错与维护。

💡

Aha：用“责任”给 AI 指路

三份真实清单，画出三条边界

注册表管“怎么启动”，endpoint 配置管“去哪里连”，根依赖管“客户端必须带什么”。三者相邻，但责任不混用。

定义一张不可随意改写的“服务运行卡”。

卡上先写唯一服务名，再写它的 runtime 在哪里。

接着记录 uv run 之后真正执行的命令。

每张卡有默认端口；没有特别声明时，默认需要 GPU。

② endpoint 配置：客户端 → 网络地址

endpoints:
  graspgen:  { host: 127.0.0.1, port: 5557 }
  graspgenx: { host: 127.0.0.1, port: 5559 }
  fastfs:    { host: 127.0.0.1, port: 5556 }
  sam3:      { host: 127.0.0.1, port: 5558 }
白话翻译

这是一份 YAML 地址簿，endpoints 是所有服务地址的总栏目。

graspgen 与 graspgenx 都在本机，但各用自己的端口。

fastfs 和 sam3 也独占端口，因此四个服务可以同时运行。

白话翻译

这是根项目安装时会带上的公共依赖清单。

NumPy 处理数组；MessagePack 负责紧凑地打包数据。

PyYAML 读取配置；Pydantic 检查数据是否符合契约。

情境演练：先定改动边界

每题都像一条真实任务单。选择最能保持分层清楚、又不漏掉相关文件的做法。

1. sam3 要新增可选字段 crop_mode，而且旧调用仍要工作。你会怎样给 AI 划定范围？

2. graspgen 在新 GPU 驱动上需要另一组 Torch / CUDA 版本，但普通客户端不该下载它们。最稳妥的改动是什么？

3. 只有你的电脑需要把 graspgen 从本机改连到实验室服务器。应该怎样做？

4. 团队总结出一套所有服务都适用的“连接失败排查清单”，以后还会持续补充。放在哪里最合适？
