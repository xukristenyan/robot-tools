Aha：contract 是双方共用的“兼容护照”

它的 schema 同时约束请求和响应；任意一端偷偷换格式，护照检查就会暴露问题。

200 已签收：请求处理成功，可以继续检查结果内容。
422 清单不合格：请求没通过 schema 检查，通常还没进入 handler。
500 办理中出错：服务端内部失败，查看 handler 或 backend 日志。这里的数字叫 status code。

排错时，先问“包裹走到哪一站了？”

没发出就看 client；422 看 request contract；500 看 handler 与 backend；成功返回却无法读取，就对照 response contract。

真实代码：寄件端先整理，再封箱

左边是项目原码，右边把每一次交接翻译成日常语言。

右图也执行完全相同的本地整理。

把有效迭代次数原样写进寄件单。

把最大视差限制也写进去。

请求模型装填完成。

CODE · wire.py 
def pack(payload: object) -> bytes:
    return msgpack.packb(payload, default=msgpack_numpy.encode, use_bin_type=True)

def unpack(raw: bytes) -> object:
    return msgpack.unpackb(raw, object_hook=msgpack_numpy.decode, raw=False)
白话翻译

定义 pack：输入一个 payload 对象，输出字节。

MessagePack 负责封箱；msgpack_numpy 专门处理 NumPy 数据。

两种方向在这里对称相遇。

定义 unpack：输入原始字节，输出对象。

MessagePack 负责拆箱；NumPy 解码助手把数组恢复回来。

真实代码：收件端只处理自己的那一棒

FastFSServer 不负责网络封箱；它接到合格请求后，决定走假结果还是调用真实 backend。

CODE · server.py 
@handler(ReconstructRequest)
def reconstruct(self, req: ReconstructRequest) -> ReconstructResponse:
    if self._fake:
        H, W = req.left.shape[:2]
        return ReconstructResponse(disparity=np.zeros((H, W), dtype=np.float32))

    disp, _timings = self.backend.infer(
        req.left,
        req.right,
        valid_iters=req.valid_iters,
        max_disp=req.max_disp,
    )
    return ReconstructResponse(disparity=disp)
白话翻译

装饰器把这类请求登记给这个 handler。

定义 reconstruct：收请求，承诺返回 ReconstructResponse。

如果开启 fake 模式……

先读出左图的高度 H 和宽度 W。

直接返回一张 H × W 的全零 float32 视差图。

否则进入真实计算路径。

调用 backend 的 infer，接收视差和计时信息。

把左图交给 backend。

把右图也交给 backend。

传入请求中约定的迭代次数。

传入请求中约定的最大视差。

backend 调用结束。

最后仍按 contract 包成响应模型，不把裸数组直接扔回去。

边界越清楚，故障范围越小

client 管输入，contract 管格式，wire 管字节，route 管接入，handler 管协调，backend 管计算。

现在轮到你：包裹卡在哪一站？

四个新故障都发生在不同边界。选择最先该检查的位置，再看解释。

1. 左图是 float64，调用在发出 HTTP 请求前就报告形状或转换错误。第一站查哪里？

2. 请求收到 422，而 FastFSServer.reconstruct 的第一行日志从未出现。最合理的判断是？

3. 请求通过验证，但真实模式返回 500；日志停在调用 backend.infer 之后。下一步最有效的是？

4. HTTP 已成功返回，拆包后却提示 disparity 的 dtype 与响应约定不符。优先比较哪两处？
