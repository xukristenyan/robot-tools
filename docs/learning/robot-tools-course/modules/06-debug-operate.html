出问题时怎么查：从症状倒推层级

像飞行员看仪表和黑匣子一样，用证据缩小范围，不靠随机拆零件。

驾驶舱里，五块仪表各看一层

红灯亮起时，第一步不是“先重装试试”，而是确认哪块仪表变红。每份证据都有自己的观察范围。

📡

status

看远端能否连接，以及“它到底是谁”。

🩺

doctor

看本机 runtime 有没有装对、同步对。

⚠️

typed exception

看这一次调用，是连接、等待、容量还是远端计算出了问题。

🏷️

request_id

把客户端错误对准服务端的 日志 与 traceback。

🧪

regression test

把修复变成可重复执行的承诺，阻止旧故障返航。

💡
证据优先，猜测靠后

一份证据只回答一个范围明确的问题：status 看远端身份，doctor 看本机状态，exception 与 request_id 看单次调用，测试守住修复。

Connect error

先用 status 核对 endpoint，再确认进程是否启动、地址是否写对。

🪪

Protocol mismatch

连接已经成功；接下来比较 health 里的服务身份与 protocol，检查 compatibility。

🚦

503 Busy

服务活着，但 admission 拒绝了请求。看并发与 capacity，不要先改 contract。

🔒

Doctor marker mismatch

这是本机 runtime 证据。对照 profile、lock 与 real marker，再决定是否重新同步。

🔥

500 Inference

带着 request_id 查服务端 traceback，确认错误是在 handler 还是 inference backend，而不是凭空重启。

⏱️

Timeout

超时只说明“等太久”，还要用 status 和 request_id 区分网络慢、排队或计算慢。

def test_install_initializes_only_services_in_profile(tmp_path, monkeypatch):
    profile = _write(tmp_path, "services:\n  - name: sam3\n  - name: fastfs\n")
    initialized = []
    synced = []
    scripts = []
    monkeypatch.setattr(launcher, "_init_upstream", lambda spec: initialized.append(spec.service_id))
    monkeypatch.setattr(launcher, "_sync_one", lambda spec, extras: synced.append((spec.service_id, extras)))
    monkeypatch.setattr(
        launcher,
        "_run_runtime_script",
        lambda spec, script: scripts.append((spec.service_id, script)),
    )

    launcher.install(Path(profile))

    assert initialized == ["sam3", "fastfs"]
    assert synced == [("sam3", []), ("fastfs", [])]
    assert scripts == [("sam3", "install.sh"), ("fastfs", "install.sh")]
